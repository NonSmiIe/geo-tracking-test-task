# SRE lens (raw)

Raw output of the operations lens. Triage in [ideas](../ideas.md).

The Operations axis can go from level 1 to about 4 with six changes. Below they are ranked by value per effort, followed by the blind spots that could hide an incident during the current load run. Nothing here re-opens a settled decision. This was a read-only review: I changed no files and ran nothing.

## Ranked changes

**1. Prometheus-format `/metrics` on every process, replacing the NATS scatter-gather.** Cost: about 1 day.
- **Files:** `metrics.py` (rewrite on `prometheus_client`), `api/health.py`, `gateway_app.py`, `processor.py` (it serves no HTTP today, so it needs `start_http_server(9100)`), `ingest.py`, `gateway.py`, `db.py`. Delete `serve_metrics`, `gather_metrics` and `merge` from `bus.py`. `scripts/benchmark.py` then reads its deltas from Prometheus with `increase()`; change it only after the current run finishes.
- **Metrics (keep `role` and `instance` as target labels, not app labels):**
  - `fleet_ingest_reports_total{transport=ws|http|batch, outcome=acked|overloaded|invalid|produce_failed}`
  - histograms `fleet_ingest_produce_seconds` and `fleet_ingest_admission_wait_seconds`
  - gauges `fleet_ingest_window_inflight` and `fleet_ingest_window_capacity`
  - `fleet_http_requests_total{route,status}`, labelled by route template, not raw path
  - `fleet_processor_records_total{outcome=committed|stale|duplicate|replayed}`
  - histograms `fleet_processor_batch_seconds` and `fleet_processor_freshness_seconds` (commit time minus report timestamp). This is the server-side SLI that is missing today.
  - `fleet_processor_assigned_partitions`, `fleet_processor_rebalances_total`
  - `batches_failed`, `publish_retries` and `commits_lost` as `_total` counters
  - `fleet_db_pool_in_use`, `fleet_db_pool_timeouts_total`
  - gateway: `fleet_gateway_sessions`, `_subscriptions`, `_bytes_enqueued_total`, `fleet_gateway_evictions_total{reason=queue_full|send_deadline}`, `fleet_nats_slow_consumer_total` (via a NATS `error_cb`)
  - `fleet_event_loop_lag_seconds` histogram on every role
- **Why histograms instead of the current deques:** a p95 over "the last 4,096 batches" has no time base and cannot be combined across instances. `histogram_quantile(sum by (le))` works over any time window and any number of replicas.
- **What it proves:** standard, aggregatable telemetry.
- **How to verify:** `curl :8000/metrics | promtool check metrics`, plus a test that parses the exposition after one processed batch.

**2. An `observability` compose profile.** Cost: about 1 day.
- **Containers:** Prometheus (scrapes each replica through `dns_sd_configs` on the `api`, `gateway` and `processor` service names), Grafana with a provisioned datasource and dashboard JSON, `kafka-exporter`, `postgres-exporter` and `prometheus-nats-exporter` (reading `:8222`).
- **HAProxy:** add a `frontend stats` on `:8404` using HAProxy's built-in `prometheus-exporter` service.
- **Dashboard rows, each answering one operational question:**
  - **Keeping up?** offered vs acked vs committed per second.
  - **How far behind?** lag per partition, in records and in seconds, with a line at the retention limit.
  - **Fast enough?** freshness p50/p95/p99.
  - **Shedding load?** 503 rate, window fill ratio, admission wait p99, the HAProxy backend queue.
  - **Dashboards healthy?** sessions, evictions by reason, NATS slow consumers.
  - **Is the database the limit?** pool in use vs pool size, pool timeouts, HOT ratio and dead tuples on `device_latest`.
  - **Balanced?** per-replica ingest max/mean, partitions per processor.
  - **Loop lag** p99 by role.
- **How to verify without a browser:** `curl :9090/api/v1/targets | jq` shows every target up; `GET /api/dashboards/uid/fleetline` returns 200; a 60 s generator run gives a non-zero result for `sum(rate(fleet_ingest_reports_total{outcome="acked"}[1m]))`.

**3. Alert rules with `promtool test rules` unit tests.** Cost: about half a day. Tested alerts are what a reviewer rarely sees.
- **Lag near retention:** `kafka_consumergroup_lag` converted to seconds (lag divided by the ingest rate) exceeds half of `log.retention.ms`.
- **Partitions unowned:** `sum(assigned_partitions) < 24` for 1 minute.
- **Lag growing:** `deriv(lag[5m]) > 0` for 10 minutes.
- **Ingest shedding:** overloaded divided by total exceeds 1% for 2 minutes.
- **Window saturated:** in-flight over capacity above 0.8 for 2 minutes.
- **Eviction rate:** evictions above 0.1/s.
- **Pool timeouts:** any increase over 1 minute.
- **Batch failures:** any increase over 5 minutes.
- **Freshness:** p95 above 1 s for 5 minutes (the acceptance v3 bound).
- **NATS slow consumers:** any increase.
- **Target down:** `up == 0`.
- **Files:** `ops/prometheus/rules.yml` and `rules_test.yml`. Alertmanager is not needed; `/api/v1/alerts` is enough to show them.

**4. A runbook section in the README, one entry per alert.** Cost: about 2 hours. Each entry gives the meaning, the first query to run and the action. For example, lag near retention: scale `PROCESSORS` up to 24, check database CPU, and know that the cliff is `KAFKA_LOG_RETENTION_MS` (DA2 is still open). Also cover a processor restart and the existing repartition procedure. The only cost is wording, and it ties items 1–3 into a story.

**5. Structured JSON logs.** Cost: about half a day.
- One `logging` config shared by all roles, with an orjson formatter carrying `role`, `instance` and `event`.
- The batch id is deterministic: `partition:first-last offset`, so a replay shares the id of the original batch.
- Add a `ConsumerRebalanceListener` that logs assigned and revoked partitions. Rebalances are invisible today.
- Log each gateway eviction with connection, user, reason and queued bytes.
- HAProxy sets `unique-id-format` / `X-Request-ID`, and the api logs only 5xx and overload responses, with that id. The access log stays off.
- **How to verify:** `docker compose logs processor | jq -e .`, plus `caplog` tests.

**6. Processor health, and a clear statement of readiness semantics.** Cost: about half a day.
- The processor has no healthcheck. Give it liveness as "last poll within `publish_deadline + 10 s`", exposed on the item 1 server. Readiness must not depend on having partitions assigned, because a processor beyond 24 partitions is idle and still healthy.
- Write k8s manifests in `deploy/k8s/`:
  - probes on `/health/live` and `/health/ready`
  - `migrate` as a Job
  - `terminationGracePeriodSeconds: 45` plus a `preStop` sleep
  - a PodDisruptionBudget on processors
  - KEDA autoscaling on Kafka lag, capped at the partition count
  - the compose security context carried over
- **How to verify:** `kubeconform`.

## Blind spots that could hide an incident during a load run

- **Processes can silently drop out of `/metrics`.** It waits 0.3 s for replies over NATS. A process that is stalled or reconnecting simply does not answer, so role totals shrink and nothing reports how many instances replied out of how many expected. During a NATS outage `/metrics` returns nothing.
- **Counters restart from zero on a process restart.** Each restart creates a new instance id, so the benchmark's baseline-delta method under-counts across any restart (it will matter for the G5 fault runs).
- **Lag is only reported by the processors themselves.** Dead or stuck processors report nothing, and partitions nobody owns are not counted, so `consumer_lag` falls just as the group gets worse. With the 30-minute retention, acked reports can be deleted without any signal.
- **No healthcheck on the processor.** One stuck for up to 30 s in the publish retry, or hung on the database, still shows as Up.
- **Pool waits, REST 503s and the HAProxy queue are not measured.** Database pool waits, REST 503 responses and connections queued at the edge beyond `maxconn 4096` are all invisible.
- **NATS slow-consumer drops at the gateway are not counted.** The NATS server exposes them on `:8222`, but nothing reads them. Reconciliation would catch the missing data but not the cause.
- **Server-side latency has no time base.** The p95 is over the last 4,096 batches, not a time window. The only end-to-end latency comes from the benchmark's four observers.
- **The README is wrong about gateway readiness.** It says readiness checks NATS, but `gateway_app.py` always returns ready.
