# Fleetline security review

I found no cross-tenant leak and no injection. The real risks are cheap ways to exhaust shared resources, plus device spoofing. One finding stops the pipeline for every user.

## Critical

**C1. A zone's radius has no upper bound, so one user can stall every processor.** `Radius` is only `gt=0` (`schemas.py:10`, `:63`). A user creates 1000 zones (the quota, `settings.py:36`), each with `radius_m=2e7`, which covers the whole earth. Every report then matches 1000 zones, so `MATCH_SQL` (`spatial.py:19-32`) returns about 2M rows for one 2,000-record batch. That most likely exceeds the 2 s `statement_timeout` (`db.py:19`). The lane then seeks back and retries forever (`processor.py:206-214`), and every partition becomes poison. If the query does finish, the processor still builds 2M alert dicts per batch in Python. The quota does not bound alert volume the way the decision log assumes. Fix: cap the radius in `Radius` and with a DB `CHECK`, for example at 50 km. Also cap the total footprint area per user at CRUD time, which fits the rule that load bounds sit where load originates.

## High

**H1. One client can take the whole shared ingest pipeline.** The edge has no rate limit (`haproxy.cfg:22-27`). Socket admission waits with no timeout (`ingest.py:172-173`), and the window serves waiters in FIFO order (`ingest.py:59-60`). A client with about 8 `/ingest` sockets per replica therefore holds the 8192-report window (`settings.py:23`). HTTP clients queue behind it and get 503 after 1 s. A sustained flood also grows consumer lag past the 1 GiB-per-partition retention (`docker-compose.yml:58`), so Kafka deletes other devices' acknowledged reports before they are read. Fix: per-socket token bucket in `Ingest.stream`, a `timeout` on `admit`, and the edge limits below.

**H2. A gateway can be OOM-killed, and one user can take every dashboard slot.** The per-connection queue is 8 MiB × 128 connections = 1 GiB (`settings.py:37,39`). The container limit is 320 MiB (`docker-compose.yml:131`), and each NATS subscription may buffer 256 MiB (`gateway.py:138`). A world viewport subscribes to `fleet.pos.>` (`tiles.py:46`), which at 60k positions/s is about 3.6 MB/s per socket. About 40 sockets that stop reading fill up during the 2 s send timeout, and the kernel kills every dashboard on that replica. Nothing caps connections per `user_id` (`gateway.py:175`). Fix: 1 MiB per-connection queue, a gateway-wide byte budget that evicts the largest queue first, a per-user connection cap, and a `pending_bytes_limit` that is a fraction of `mem_limit`.

**H3. Device spoofing can hijack a device and fake alerts.** `/locations` and `/ingest` take no identity (`locations.py:46,66`). Timestamps may be up to 5 min in the future (`schemas.py:15,29-31`), and the upsert is monotonic (`spatial.py:43`). An attacker who sends a fake position stamped now+5 min every 5 min freezes any device, because every genuine report counts as stale. The same attacker can drive fake devices into anyone's zone and trigger alerts. Demo device ids are derived from `uuid5(user_id)` (`demo.py:39-42`), so they are predictable. A real design needs per-device credentials (mTLS or a signed token bound to `device_id`), a device→owner table, and a check that the credential matches each report's `device_id`. Small fix now: stamp `reported_at` as `min(timestamp, server receive time)`. Suggested README line: *"Ingestion is unauthenticated: any client can report any `device_id`. Positions and alerts are only as trustworthy as the network that reaches `/ingest`."*

**H4. Request bodies outside ingest are unbounded.** `POST`/`PATCH /geozones` goes through pydantic, which reads the whole body (`geozones.py:48,102`). The edge has no size cap. One 1 GB upload OOM-kills an api replica (320 MiB). Fix: in HAProxy, `http-request deny deny_status 413 if !{ path_beg /locations } { req.hdr_val(content-length) gt 16384 }` and deny chunked bodies on those paths. Alternatively, apply one ASGI size limit to every route.

## Medium

- **M1. Slowloris.** No `timeout http-request` or `http-keep-alive` is set (`haproxy.cfg:10-20`), so idle sockets hold connection slots for 60 s, up to `maxconn 20000`, and upgraded sockets idle for an hour (`timeout tunnel 1h`).
- **M2. Viewport churn.** Each viewport message takes the gateway-wide lock and sends SUB/UNSUB to NATS (`gateway.py:126-141,163-172`), with no rate limit. One socket sending 10k messages/s stalls routing for every connection on that replica. Fix: drop a viewport that arrives sooner than 250 ms after the previous one, and lower the gateway's `--ws-max-size` to about 1 KiB (`Dockerfile:15`).
- **M3. One user can exhaust the database pool.** Each api replica has 5 connections with a 1 s `pool_timeout` (`db.py:14-16`). A large sparse bbox (`grid_cells` returns NULL, `003:22`) scans in `device_id` order until the 2 s timeout (`devices.py:67-72`). `/insights` runs `count(*)` over all of `device_latest` plus 50 occupancy scans per call (`insights.py:6-23`), and with whole-earth zones (C1) each occupancy scan reads the whole table. A few such clients return 503 to everyone. `device_latest` also grows without limit from random spoofed ids. Fix: a per-user request rate at the edge, a cache for the fleet aggregate, and a TTL sweep of stale devices.
- **M4. Grafana default admin password plus a superuser database role.** `GF_SECURITY_ADMIN_PASSWORD` defaults to `local-demo-password` (`docker-compose.yml:162`). The api, processor and exporter connect as superuser `geo` (`:14,30,189`). A DNS-rebinding page can reach Grafana on 127.0.0.1:3097, log in as admin, add a Postgres datasource for `db:5432`, and run `COPY … FROM PROGRAM`, which executes commands in the db container. Fix: `${GRAFANA_PASSWORD:?}`, `GF_AUTH_DISABLE_LOGIN_FORM=true`, `GF_SERVER_ENFORCE_DOMAIN=true`, and separate non-superuser roles for the app and the exporter (the exporter needs `pg_monitor`).
- **M5. `/stats` is anonymous and not cached.** Every call sends 3 Prometheus queries (`health.py:31-46`), so flooding it can overload Prometheus and blind the alerts. Fix: cache the result for 5 s per process.

## Low

- **Demo.** Four users restarting demos every 120 s can keep the global slots (`demo.py:74-82`) and lock out everyone else. The demo's zone upsert skips the zone quota (`demo.py:92-112`).
- **Third-party containers are not hardened.** db, kafka, nats, edge, prometheus, grafana and the exporters have no `cap_drop` or `no-new-privileges`. NATS has no auth, so any compromised container on the network can publish to any user's alert subject.
- **Docker Desktop hides client IPs.** It NATs host traffic, so HAProxy sees one source IP for everyone and per-IP limits collapse into a single bucket. Key the limits by user, or deploy with real client IPs.
- **Clean, checked:** zones, alerts and `zones_changed` are scoped by `user_id`; NATS subjects hex-encode the id (`bus.py:21-25`); viewports yield only `pos` subjects; every SQL statement uses bound parameters and there is no `LIKE`; PromQL strings are constants; logs go through `orjson`; the UI writes with `textContent`; `pg_stat_statements` holds only normalized statements; Kafka, NATS and Postgres publish no ports; app containers are read-only, cap-dropped and non-root.

## Proposed HAProxy limits

```
frontend fleetline
    timeout http-request 10s
    timeout http-keep-alive 5s
    stick-table type ip size 200k expire 60s store conn_cur,conn_rate(10s),http_req_rate(10s),bytes_in_rate(10s)
    tcp-request connection track-sc0 src
    tcp-request connection reject if { sc0_conn_cur gt 256 } || { sc0_conn_rate gt 200 }
    http-request deny deny_status 429 if { path /ingest } { sc0_conn_cur gt 16 }
    http-request deny deny_status 429 if { sc0_bytes_in_rate gt 20000000 }
    http-request track-sc1 req.hdr(x-user-id) table per_user if { req.hdr(x-user-id) -m found }
    http-request track-sc1 url_param(user_id) table per_user if { path /ws }
    http-request deny deny_status 429 if { sc1_http_req_rate(per_user) gt 100 }
    http-request deny deny_status 429 if { path /ws } { sc1_conn_cur(per_user) gt 8 }
backend per_user
    stick-table type string len 96 size 100k expire 10m store http_req_rate(10s),conn_cur
```

The edge counts only upgrades, not frames. The frame rate on `/ingest` still needs the in-app token bucket.

## Top 5 fixes to do now

1. Cap `radius_m` in the schema and with a DB `CHECK`, and bound the total zone area per user (C1).
2. Add the HAProxy limits above, plus a per-socket token bucket and an admission timeout in `Ingest.stream` (H1, M1, M3).
3. Bound gateway memory: 1 MiB per-connection queue, a gateway-wide byte budget, a per-user dashboard cap and a throttled viewport (H2, M2).
4. Cap request body size for every route at the edge (H4).
5. Clamp future timestamps to server receive time and add the spoofing line to the README. Remove the Grafana password default, disable its login form, and give the services non-superuser DB roles (H3, M4).
