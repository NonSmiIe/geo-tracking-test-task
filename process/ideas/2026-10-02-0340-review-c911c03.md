I found no data-loss or security defects in this commit. I found three medium defects (one is borderline), three rule violations and three claims in the message that the diff doesn't fully deliver. I read the commit and the code only; nothing was run.

## 1. Defects

**D1. A replica that restarts or scales down causes failed requests.** `edge/haproxy.cfg:6-14` and `:24`/`:29`
- The config has no `option redispatch` and no faster health check. The defaults are a check every 2s, down after 3 failures, plus DNS `hold valid 5s`.
- Scenario: an api replica gets SIGTERM, or crashes and restarts under the new `restart: unless-stopped`. Uvicorn stops listening at once. HAProxy keeps sending new requests to that slot for about 6s. Its connect retries all go to the same dead server, so clients get `503`.
- During a run, the generator counts these as dropped reports.
- Fix: in `defaults`, add `retries 3`, `option redispatch 1` and `default-server inter 1s fall 2 rise 2 on-marked-down shutdown-sessions`.

**D2. The connection cap was dropped without saying so.** `geo_tracking/__main__.py` (deleted), `docker-compose.yml:96`
- The old launcher set `limit_concurrency=4096`. The new uvicorn commands don't, and HAProxy sets no per-server `maxconn`.
- Scenario: a flood of device sockets or HTTP connections reaches one 320 MB replica with no limit, apart from HAProxy's global 20000. On `/ingest` the only bound is `ingest_window` per socket, so memory grows until the container is OOM-killed.
- Fix: put the cap at the edge with `default-server maxconn N`, which queues instead of killing the replica. Don't add it back as a uvicorn flag.

**D3 (borderline medium). Slow-dashboard eviction now waits behind buffers the gateway can't see.** `edge/haproxy.cfg` (whole file)
- The gateway's 2s `send_timeout_seconds` measures writes to HAProxy, not to the browser. Two kernel socket buffers (each can grow to several MB) plus HAProxy's own buffer now sit in between.
- Scenario: a slow browser can fall megabytes behind before `send_text` blocks. The per-connection bound (`websocket_queue_bytes`) no longer limits how stale that client's data gets, and eviction comes late.
- The eviction test (`tests/test_gateway.py`) connects to the gateway directly, so it can't catch this.
- Fix: set small `tune.sndbuf.client` and `tune.rcvbuf.server` in `global`.

**Checked and fine:**
- WebSocket tunnelling: uvicorn's default 20s ping keeps both kinds of socket active, so `timeout tunnel 1h` never trips.
- The `server-template`/`init-addr none` setup, the metrics role rename (`acceptance.py`, `drive.py`), and the frontend's `/ws` (same origin, so it goes through the edge).
- Future-timestamp check: generator and demo timestamps are never later than now, and the tests' fixed `START` is in the past.

## 2. Rule violations (G3)

- **The uvicorn flags are written three times.** `docker-compose.yml:96` defines a `&serve` anchor that nothing references. Line 115 repeats the same flags for the gateway, and `Dockerfile:15` has a third command that has drifted (no `--ws-max-size`, no `--no-access-log`). Fix: one parameterised command (for example `command: [uvicorn, "${APP}", …]`) and drop the Dockerfile `CMD`, or make it the one source.
- **`/health/database` (`geo_tracking/api/health.py:29`) has no caller.** No compose healthcheck, HAProxy check, test or script uses it, and it returns `{"status": "ready"}`, which is misleading. Delete it or wire it to something.
- **README is now wrong, which breaks the CLAUDE.md rule to keep it true.**
  - `README.md:96` still says readiness checks NATS, Kafka and PostgreSQL.
  - `:47`, `:54` and `:73` still talk about "api workers".
  - `:95` says the demo is "shared across workers".
  - The edge and gateway services don't appear in it at all.

## 3. Commit message versus diff

- **"one forged report cannot freeze a device's watermark"** is overstated. A report dated 4m59s ahead is accepted and still freezes that device for up to five minutes. The diff bounds the freeze; it doesn't prevent it.
- **"scale with replicas instead of uvicorn workers"** holds only up to 16 replicas per service. The `server-template … 16` cap is hard-coded, and a higher `API_REPLICAS` or `GATEWAYS` gets no traffic on the extra replicas, with no warning.
- **"a database outage no longer drains ingest"** is true. But the message leaves out that api readiness also stopped checking NATS, and that the concurrency cap was removed (D2).
