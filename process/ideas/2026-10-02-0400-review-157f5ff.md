Four findings at medium or higher. Two are high: one can wedge an api replica permanently, the other can hang a device socket.

I reviewed `157f5ff`. While I was reviewing, HEAD moved to `f3d4391`, which only adds the 150k row to the README.

## Findings

**1. High: a failed `producer.send` permanently loses produce-window capacity** (`geo_tracking/ingest.py:118-119`)
- **What goes wrong:** `self.reserve(1)` runs before `await self.send(report)`. When the producer can't get metadata or its buffer stays full past `request_timeout_ms`, `send` raises `KafkaTimeoutError`. That exception isn't caught, so `release` never runs and the reserved slot is never given back.
- **Scenario:** the Kafka kill your new `--fault` flag injects. Every socket blocked in `send` loses one slot, and a few thousand sockets use up the whole 8192 window. When Kafka comes back, `room` is never set again: sockets block forever and every HTTP request gets 503. `/health/ready` only checks broker metadata, so the edge keeps sending traffic to the dead replica.
- **Fix:** put reserve and release in one admission method around the send, releasing when the send raises, or use a shared `asyncio.Semaphore`.

**2. High: `flush` hangs forever after a produce failure** (`ingest.py:110-111`)
- **What goes wrong:** a failed future never calls `acks.settle`, so `count` never reaches `issued` and `idle` is never set.
- **Scenario:** a device sends `flush`, the server sits in `acks.idle.wait()`, and the `failure` check is never reached. A device that waits for acks before sending more also stalls, because the loop only notices `failure` after the next `receive_text`.
- **Fix:** close the socket with 1011 as soon as `failure` is set, for example by waking `idle` and checking `failure`, or by cancelling the receive.

**3. Medium: sockets starve HTTP, and every release wakes every waiting socket** (`ingest.py:69`, `116-117`, `56-59`)
- **Starvation:** HTTP is rejected when `inflight + n > window`, while sockets wait and take each freed slot one at a time. Under socket saturation, a batch POST can never find `n` free slots and always gets 503.
- **Wake-ups:** `room.set()` fires on every release with no hysteresis and wakes every waiting socket. That is O(sockets) wake-ups per ack at 150k.
- **Fix:** use one FIFO semaphore that HTTP waits on too, with a bounded timeout, and that wakes one waiter per release.

**4. Medium: commit handling misses the usual rebalance error** (`geo_tracking/processor.py:123-127`, together with `88-98`)
- **What goes wrong:** `consumer.commit` raises `IllegalStateError` ("No partitions assigned" or "Partition … is not assigned") once the assignment has changed, which I confirmed in `aiokafka/consumer/consumer.py:580-593`. Only `CommitFailedError` is caught.
- **Scenario:** a batch spans a rebalance, such as a processor kill fault. The processor crashes and restarts, which triggers another rebalance.
- **NATS outages:** `publish` retries forever without polling. After `max_poll_interval_ms` (300 s), the heartbeat task leaves the group (`group_coordinator.py:792-795`). When NATS returns, the commit raises `IllegalStateError` and the processor crashes.
- **Duplicates:** each retry while NATS is reconnecting appends another full copy of the batch to the client's pending buffer, so frames are delivered several times and exact reconciliation fails.
- **Fix:** commit only `offsets` that are in `consumer.assignment()`. Bound the retry by the poll interval, or stop retrying when the partitions are revoked.

## Other issues (not ranked)
- **Edge** (`edge/haproxy.cfg:19`): there's no `timeout check`, so the check timeout is `inter`, which is 1 s, and `/health/ready` itself allows 1 s for Kafka metadata. With `fall 2`, two slow checks under load mark a replica down. `shutdown-sessions` then drops every device and dashboard socket on it, and they all reconnect onto the other replicas, which can cascade. Fix: `timeout check 3s`. Drop `shutdown-sessions` on gateway, since connections to a dead replica fail on their own anyway.
- **Benchmark** (`scripts/benchmark.py:110-111`): a malformed `--fault` only raises at `await injector`, after the whole 300–900 s run, and the run's result is lost. A nonzero `docker` exit code is logged but doesn't fail acceptance, so a fault that never happened can still pass. Fix: parse faults with an argparse `type` and fail the run when a fault exits nonzero.
- **Entrypoints:** all checked and fine. Compose `entrypoint` clears the image CMD, so processor and migrate start the right process. Gateway's `command` is passed to uvicorn correctly, and the tests image (`Dockerfile.test`) has no ENTRYPOINT.

## Rule violations
- **Duplicated invariant:** the window-full rule is written three ways in three places (`ingest.py:53`, `69`, `116`) instead of one admission point.
- **Flag pretending to be an error:** `failure: BaseException | None` stores a `KafkaError` that is never raised. It is only a flag and should be a `bool`.
- **Typing:** `asyncio.Future` is unparameterised (`ingest.py:61`, `85`), and `Ingest.__init__` has no `-> None`.
- **Tests:** only `Acknowledgements` got a test. The shared window, produce failure, the NATS retry and the lost commit have none.

## Commit-message claims the diff doesn't deliver
- **"The 150k rung after the edge split passes policy v3":** `evidence/capacity/rung-150k-h1.json` has `started_at` 18:44:39 UTC. That is six seconds after `c911c03` and eight minutes before this commit. The file has no `faults` key, which this commit's benchmark always writes. So the run measured the code before this commit: 16-slot templates, no `maxconn`/`retries`, no shared socket window. It doesn't validate any of the hardening here.
- **"Sockets share the per-process produce window with HTTP":** they share the counter, but not fairly (finding 3), and a failed send shrinks it for good (finding 1).
- **"Treat an offset commit lost to a rebalance as handed over":** this only covers `CommitFailedError`. The more common `IllegalStateError` still crashes the processor (finding 4).
