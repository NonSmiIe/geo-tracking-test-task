I found six medium-or-higher findings. Two of them break correctness: devices on the exact grid edges are left out, and alerts are lost for good when a batch fails to publish. I read only and ran nothing, so the plan behaviour under prepared statements is unchecked.

## Medium-or-higher findings

**1. The cell filter can drop rows that `ST_Intersects` keeps** (`migrations/versions/002_device_grid_cells.py:20,22`)
- **Where:** `row_low` and `col_low` have no upper clamp, but `grid_cell` clamps at 719 and 1439.
- **Scenario:** `south=north=90` gives `row_low=720` and `row_high=719`, so the array is empty and a device at latitude 90 is excluded. `west=180` alone or `west=180,east=10` does the same: the first span `(180,180)` has `col_low=1440`, and a device at longitude exactly 180 is lost.
- **Root cause:** the formula is written twice, once in each function, and the two copies drifted.
- **Fix:** write one cell-index expression and have both functions call it (row = `least(719, floor((y+90)*4))`, column likewise). Add a superset test like `test_footprint_candidates_equal_exact_geography_everywhere`, covering ±90, ±180, degenerate boxes and split boxes.

**2. `/insights` falls back to a geodesic full scan for antimeridian, polar and large zones** (`insights.py:16-26`, `002:20-23`)
- `ST_XMin`/`ST_XMax` of the two-box antimeridian footprint is -180/180, so it covers full-width bands of 1440 cells per row. Three or more rows go over 4096 and return NULL. Polar zones always do, and so does any zone wider than about 16°.
- The NULL branch (and the cell branch too) no longer has the `position && footprint` prefilter. Each such zone becomes a seq scan running `ST_DWithin(geography)` on every row, for up to 50 zones per call, against a 2 s statement timeout. That is a likely 500 at 1M devices.
- **Fix:** have `grid_cells` take the union over `ST_Dump(area)` parts, and keep `device.position && zone.footprint` in both branches.

**3. Bbox index use is assumed, not shown** (`devices.py:34-43,63`)
- `cell = ANY($n)` with `ORDER BY device_id LIMIT 1001` goes out as an asyncpg prepared statement. After 5 executions PostgreSQL may switch to a generic plan, which assumes about 10 array elements and may walk the primary key with a filter.
- **Fix:** run EXPLAIN (ANALYZE) on the 6th or later execution for a sparse and a dense viewport. The extra round trip in `area()` also exists only to shape the plan.

**4. HTTP admission takes permits one at a time** (`ingest.py:56-65`, `83-84`)
- An HTTP batch of N re-queues behind every waiting socket for each permit. With S sockets waiting it gets about 1/(S+1) of the releases, so 1000-report batches always time out under load (503).
- While it waits, it holds up to 999 idle permits for the full second, which shrinks the window for everyone.
- **Fix:** grant the whole count at the head of the queue (a weighted FIFO: a counter plus a deque of `(count, future)`).

**5. `PublishStalled` loses the batch's events for good** (`processor.py:104-106` with line 60)
- The DB is already committed and the offsets are not. The new owner replays the batch, `fresh` filters on `>` the watermark, and every record is stale. So positions and inside-report alerts are never sent, which breaks "alert on every fresh inside report".
- During a NATS outage this repeats: one batch is lost per processor on each restart cycle (about 120 s), and each owned partition is frozen for 120 s.
- On the way out, `nats.drain()` raises `ConnectionReconnectingError` while reconnecting. That hides the original error and skips `db.close()`.
- **Fix:** make replay re-emit events for records whose timestamp equals the watermark (the upsert stays idempotent, alerts become at-least-once). Also wrap `drain` so it cannot hide the failure.

**6. A SIGTERM mid-batch has the same loss** (`processor.py:189-193`)
- `task.cancel` cancels `run()` between the DB commit and the NATS flush, giving the outcome in finding 5. "Stop cleanly" is not delivered.
- **Fix:** set a stop event that `run()` checks before `getmany`, and let the current batch finish (DB, publish, commit). Note the 120 s publish deadline is longer than the 20 s `stop_grace_period`.

A related point: the replay path at `processor.py:129-130` calls `seek` on partitions it may no longer own, which raises `IllegalStateError` on the same rebalance the commit path now tolerates. Apply the same `owned` filter there.

## Rule violations
- **Grid formula** in two places (finding 1).
- **NULL-or-array branching** written twice: `devices.py:36-43` and `insights.py:14-27`, which itself has two near-identical subqueries.
- **Model does not match the migration:** `models.py:42` has no `postgresql_with={"fillfactor": 70}`.
- **Migration order:** `002:47` sets the fillfactor after the table rewrite, so existing rows stay packed at 100%.
- **README not updated:** it still describes no device grid. That breaks the CLAUDE.md rule "keep README true".
- **No new invariant recorded:** CLAUDE.md lacks a line saying "grid_cells must be a superset".
- **Untested paths:** nothing tests SIGTERM, `PublishStalled`, the `owned` filter or the cell edges.

## Commit-message claims not delivered
- "stop cleanly on SIGTERM": no (finding 6).
- "processors survive rebalances": the seek path can still crash.
- "releases on every exit path": not if the task is cancelled during `await self.send` (`ingest.py:139`). That only happens at shutdown, so it is low severity.
- "find every row" (the snapshot/occupancy claim): false at the 90/180 edges.
- "fall back to a scan": true, but the scan lost its bbox prefilter.
