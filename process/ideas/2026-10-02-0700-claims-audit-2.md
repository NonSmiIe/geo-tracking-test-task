# Second claims audit (raw)

Triage in [ideas](../ideas.md).

Out of roughly 120 claims I checked, about 100 hold. Ten are false, one is stale and nine have no evidence behind them. The worst problems are in the Operations runbook and the failure-campaign wording. The results tables mostly match their JSON files. I modified nothing and ran nothing.

## FALSE

- **Processor health and `ProcessorStalled`.** The README says a processor reports `stalled` "once Kafka has not been polled" and that the alert means "stuck publishing or on the database". In the code, `processor.polled` and `LAST_POLL` are set every 0.1 s by the supervisor loop (`processor.py:139-140`), not by Kafka polls (`lane()` → `getmany`). A lane stuck publishing exits after 30 s (`PublishStalled`), and a stuck database hits the 2 s statement timeout. Neither one makes the timestamp go stale; only a blocked event loop does.
- **`ProcessorStalled` action.** The README says "Its own healthcheck fails and compose restarts it". Compose with `restart: unless-stopped` restarts a container only when it exits, never because it is unhealthy, and nothing in the repo does that job.
- **Processor database pool.** The README says "processors 2" (Architecture) and "2 per processor" (Resource bounds). The code uses `Database(settings, pool_size=settings.processor_transactions)`, and `processor_transactions` defaults to 4 (`processor.py:220`, `settings.py`).
- **PostgreSQL version.** The Compose table says "PostgreSQL 17 + PostGIS 3". `Dockerfile.postgis` uses `postgres:18.0-trixie`, and the README itself relies on PG 18's `RETURNING old.*`.
- **Published ports.** The README says "Only the edge port is published". Compose also publishes Prometheus on 9097 and Grafana on 3097, both on 127.0.0.1.
- **Alert latency.** The README says alert latency is "within 3 ms of it in every run". Many runs differ by more: rung-200k-h2 p95 448 vs 457 ms and p99 768 vs 778 ms; rung-300k p95 48,728 vs 48,740 ms; rung-300k-s1 p95 753 vs 761 ms.
- **What the failure campaign checks.** The README says "Every acknowledged report must end up … in PostgreSQL, by count and timestamp sum". Fault policy v1 checks only that "PostgreSQL ends holding every device's *newest* acknowledged report" (`database_holds_every_latest_report`).
- **`GatewaySlowConsumer` action.** The README says "the browser reconnects and resnapshots". When NATS drops messages for a slow subscription, the gateway only increments a counter (`bus.counted`). It closes nothing and sends no `resync`, so the browser never finds out. The action is correct for `DashboardsEvicted`.
- **`IngestShedding`.** The README says "Over 1% of HTTP reports get 503". The rule divides HTTP `overloaded` by *all* reports, including WebSocket ones. It also leaves out the 503s for `broker_unavailable`, which are counted as `failed`.
- **Generator HTTP transport.** The README says "`--transport http` uses one `POST /locations` per report". With the default `batch_size=100` it uses `/locations/batch`; single posts happen only with `--batch-size 1` (`generator.py:242`).
- **API table.** "`GET/POST /demo`" is wrong: there is no `POST /demo`, only `GET /demo`, `POST /demo/start` and `POST /demo/stop`.
- **Fault timing.** The README says each scenario "breaks one container at 60 s". S8's `faults[0].at_seconds` is 70.68, and S2's is 62.23.

## STALE

- **Policy reference.** "The criteria were declared before the run in acceptance policy v3." The headline 300k pass and both 500k runs use `acceptance_policy: operational-v4`.

## UNSUPPORTED

- "the host was 99% busy" and "the generator plus observers [used] most of the rest of 14": nothing in the evidence records host CPU.
- "An idle-database probe puts the upsert at about 8 µs per row": no output from that probe exists. The 143 ms under load is supported (`rung-500k-s4-statements.txt`, mean 143.01).
- "HOT updates from 2% to 99%": no evidence. The 46% database CPU cut is supported (194% → 105%).
- The stated causes for rung-300k-h5 (a readiness check) and rung-300k-p8-progress (a 2M-row table): neither the logs nor the JSON record a cause. The runs did fail (h5 has `generator_dropped` 330,043).
- "The rules … are unit-tested": `rules_test.yml` covers only 5 of the 13 alerts.
- Two verdicts in the table give only part of the reason:
  - 300k-p8 also failed `kafka-1_memory_stable`.
  - 500k-s4 also failed the workload check (`scheduling_tail_fraction`, 126,796 late reports), which means the generator itself was behind.

## TRUE (spot list)

- **Results tables:** every reports/s, acknowledged count, p50/p95/p99, PostgreSQL CPU and processor CPU matches its JSON within rounding:
  - 25k, 50k and 100k at 300 s, and 100k at 900 s, all passed;
  - 150k failed on Kafka memory growth (86.6 MiB);
  - 150k-h1 (gateways 26+20 = 46%, edge 51%), 200k at 194% and 200k-h2 at 105% match;
  - 300k: about 50k/s committed while lag grew to 2.3M;
  - 500k: about 58k/s committed;
  - 500k-s4: 282% PostgreSQL, about 10.8 server cores.
- **Failure table:** every devices-resent figure and p95 matches. 648 and 805 re-emitted match `pipeline.replayed`. The S1 sessions missed events (counts below 3.6M). With resync, all four resynced at 60.91–60.93 s. In S7 one session closed, in S8 all four did.
- **"Every report reconciled" and "no scenario lost":**
  - In all fault runs, acked equals scheduled and the database holds the newest report for every device.
  - In S2–S6 the open world-view sessions reconcile the full acked set by count and checksum.
  - Every passed capacity run has `delivery_reconciled: true`.
  - One caveat: S4's `pipeline.committed` is 3,599,391, not 3.6M, with no counter reset.
- **Ingest:** murmur2_random, acks=all, idempotence, lz4, 20 ms linger; frames of 1–200 reports, rejected with 1007 before anything is admitted; ack, flush and backpressure.
- **Processing:**
  - batches of 2,000 records, 50 ms poll, 4 concurrent transactions;
  - duplicates dropped, first wins; the monotonic upsert; `consumer_progress` advanced in the same transaction;
  - order of database commit → NATS publish → offset commit, with seek-back on a database error and exit after 30 s;
  - footprint margin 1.01, a partial GiST index; `device_latest` has no spatial index (dropped in migration 002).
- **Live delivery:** zoom-8 quadkeys, at most 16 tiles, the `resync` handler and snapshot reload in `app.js`.
- **Limits and defaults:**
  - 24 partitions and 30 min retention;
  - 4 api, 2 gateway and 8 processor replicas;
  - edge `leastconn` with maxconn 4096;
  - 256 KiB body, 8,192 / 1,024 in-flight windows, 2 s statement timeout, 1 s checkout;
  - 128 sessions per gateway, 8 MiB / 2 s per session, 1,000-item alert frames, 1,000 zones per user.
- **Metrics:** every alert's metric exists in `metrics.py` or comes from an exporter; `/health/live` is the only health check; `/stats` reads from Prometheus.
- **Scaling-out table:** every row matches the code.
- **`CLAUDE.md`:** the test names and invariants match the code.

## 5 most important fixes

1. **Rewrite the processor health and `ProcessorStalled` story.** Either stamp `LAST_POLL` in each lane after `getmany` and add something that actually restarts unhealthy containers, or change the text: today the alert fires only on a blocked event loop, and nothing restarts the container.
2. **Correct the failure-campaign wording.** The check is "newest report per device in PostgreSQL, plus full delivery to open sessions", not "every acknowledged report in PostgreSQL".
3. **Fix the false numbers:** PostgreSQL 17 → 18, processor pool 2 → 4, "within 3 ms" → the real gap (up to about 12 ms), and the "at 60 s" fault timing (S8 was 70.7 s).
4. **Fix the runbook:** the `GatewaySlowConsumer` action (no resync happens, or make the gateway send `resync` on a slow-consumer error), and the `IngestShedding` description or its denominator (HTTP only).
5. **Remove or back up the unsupported capacity prose** (host 99%, the 8 µs probe, HOT 2→99%, the h5 and p8-progress causes), add the missing verdict reasons for 300k-p8 and 500k-s4, and change the policy reference to v4.
