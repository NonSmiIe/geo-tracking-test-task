# Review of bcce466 (raw)

Fresh-context reviewer, static read of `processor.py`, `spatial.py`, `bus.py`, `tests/test_processor.py` and aiokafka 0.14.0 source. Triage: [ideas](../ideas.md). Decision it reviews: [decisions](../decisions.md) (one database writer per processor).

## Defects, most severe first

1. **High: the member can stop consuming forever while the watchdog stays quiet** (`processor.py:186`, `:235`).
   - `consume()` waits on `consuming.wait()` outside `getmany`, so aiokafka's `fetcher_idle_time` keeps growing. `ensure_active_group` refuses to rejoin once the idle time reaches `max_poll_interval_ms` (300 s), and then sleeps and loops forever (`group_coordinator.py:723`).
   - How it happens: a revoke lands, then Kafka is out for 5 minutes or more, or the coordinator is unknown. When Kafka returns, the member never rejoins, `consuming` stays clear, and the watchdog never checks.
   - The lanes never had this problem, because they always sat inside `getmany`.
   - Fix: delete the gate and call `getmany` unconditionally. aiokafka already holds back records during a reassignment (`fetcher.py:1215`). Give the watchdog a check that does not depend on `consuming`.
2. **High (depends on data shape): one oversized NATS message causes a crash loop** (`:141`, `:166`).
   - Position frames are not chunked; only alerts are, by item count. A batch can now hold up to 10,000 records across partitions, so a fleet concentrated in one zoom-8 tile reaches the 1 MB `max_payload`.
   - `MaxPayloadError` is a subclass of `nats.errors.Error`, so it is retried for 30 s, then `PublishStalled`, an exit, and the replay rebuilds the same batch. Nothing is published, forever.
   - The benchmark spreads devices out, so it cannot hit this.
   - Fix: chunk frames by bytes (≤ 256 KB) and treat `MaxPayloadError` as fatal.
3. **Medium: the drop-across-revoke branch either never runs or loses records** (`:192`).
   - During a real rebalance aiokafka returns no records, and the new `Assignment` re-reads committed offsets.
   - If the branch does run, the records belong to the current assignment and the position has already moved past them, so `continue` skips those offsets for good.
   - The test at `tests/test_processor.py:61` covers behaviour aiokafka does not have.
   - Fix: delete the branch and the test.
4. **Medium: the revoke wait is too short, and late batches leak into the next generation** (`:259`).
   - Up to three batches can be in flight, each with its own 30 s deadline, but the revoke waits 30 s in total.
   - A late commit can drop commits for partitions this member still owns (`IllegalStateError`). If the member got the partition back, the committed offset can move backwards.
   - Fix: on timeout, cancel both stages, drop whatever was in flight (replay covers it), and start new stages. Put `begin`/`end` in `try/finally`.
5. **Medium: the DB-error path** (`:197`–`205`).
   - (a) `seek` on a partition that is no longer assigned raises inside the `except` block.
   - (b) A degraded database times out a full-size batch on every retry, so the loop never makes progress.
   - Fix: seek only assigned partitions; halve `max_records` on failure and grow it back on success (AIMD).
6. **Low: watchdog false positive.** `polled` spans `write` plus the `outbox.put` wait, which can last a full publish deadline. Fix: separate liveness bounds for writer and delivery.
7. **Low: shutdown can race a rebalance.** A concurrent assign sets `consuming` again during the shutdown revoke. Fix: assign does nothing once stopping.

## Adaptive batching

Batches grow only by self-clocking:
- With `fetch_min_bytes=1` the broker answers immediately.
- So a batch is about arrival rate × the time of one cycle, and the 10,000 cap is never reached (432 rows measured).
- There is no floor.

Fix: `fetch_min_bytes` about 512 KB and `fetch_max_wait_ms` about 100 ms, together with the AIMD from #5.

## Correct, leave alone

- **Batch order.** DB commit, then NATS publish and flush, then Kafka commit; the single in-order `deliver` keeps it.
- **`begin()` timing.** It runs synchronously right after `getmany`, so no revoke can slip in between.
- **Commits during the revoke callback work.** Eviction comes back as `CommitFailedError`, which is caught.
- **Seek on DB error.** It deletes the buffered `FetchResult` (`fetcher.py:1318`), so the retried batch is contiguous.
- **No loss across a real rebalance**, including reassignment to the same member.
- **Replay classification.** `consumer_progress` is read and advanced in the same transaction with `greatest()`.
- **Freshness.** Taken from the monotonic upsert's `RETURNING old.reported_at`.
- **Pool size.** `pool_size=1` matches the single writer.
