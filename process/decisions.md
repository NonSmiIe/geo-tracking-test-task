# Fleetline decision log


Settled choices for Fleetline. Read before proposing any change; re-raise only with new evidence. Format: decision, why, rejected alternatives, revisit when. Charter: loop charter. Ledger: [loop-ledger](loop-ledger.md). Plan: [plan-2026-10-02](plan-2026-10-02.md).

## Scope (Denis, 2026-10-02)

- **OpenAI assistant and CI deleted.** Not part of the assignment. Do not reintroduce them.
- **Kept:** `evidence/` (proof of checks, never deleted), `/insights`, the dashboard UI, `DESIGN.md`, `PRODUCT.md`, `.impeccable`, `.agents`, and the guided demo.
- **Capacity target:** as high as this laptop sustains, aiming at 1M devices. Measured on the laptop as it is, with no CPU pinning.
- **Browser runs approved for the night loop:** Playwright, one session per round, closed afterwards.

## Architecture

- **Kafka for ingest.** It gives partitioned durable log ownership and group rebalancing out of the box, which removes the latest-position race without a single process. *Rejected:* Redis Streams (partition ownership would be hand-rolled); a single process (ceiling of about 4k reports/s, measured at 48% of one core at 2k/s). *Revisit:* never for this assignment.
- **NATS core for fanout.** Subject-based routing on map tiles (`<prefix>.pos.<quadkey>`) and per user means the broker filters, not the gateway. *Rejected:* Kafka for fanout (every gateway decodes the full stream); Redis pub/sub (single-threaded at high fanout); JetStream (live events are ephemeral, and Kafka already is the log).
- **Alert on every fresh inside report.** This follows the assignment's wording. Grouping into «внутри с …» is a UI concern. *Rejected:* entry-only alerts in the backend.
- **Load bounds sit where load originates.** A per-user zone quota at CRUD, bounded per-connection queues, and eviction of slow sockets. *Rejected:* a match/output budget inside the ingest transaction. It let one user with more than 21 overlapping zones stop ingestion for the whole fleet (proven live, 400/400 got 503).
- **Zone matching.** A generated conservative lon/lat footprint box (GiST) as the candidate filter, then exact `ST_DWithin` on geography. *Rejected:* power-of-two radius buckets with btree_gist (correct, but non-standard and harder to review).
- **At-least-once processing.** Offsets are committed after the DB commit and the NATS flush. A DB failure seeks back and replays. Replay is idempotent via watermarks and the monotonic upsert.
- **No PgBouncer.** About 28 long-lived pooled connections against `max_connections=200`. At 1M the limit is write throughput, which PgBouncer does not improve. Transaction pooling also breaks asyncpg prepared statements. *Revisit when:* API or processor instances grow so far that the sum of their pools nears the Postgres connection limit.
- **No response cache on ingest.** Every report is unique, so there is nothing to cache. A viewport snapshot cache is allowed only if the profile shows repeated identical snapshot reads.

- **PostgreSQL write scaling with Citus** (decided 2026-10-02, Denis asked, the loop recommended, no objection). `device_latest` becomes a distributed table on `device_id`; `geozones` becomes a reference table replicated to every worker, so the match join stays local to each shard. Compose runs a coordinator and 2 workers. *Rejected:* app-level sharding, which duplicates the shard map in code; one larger primary, which does not scale out. *Order:* after H1, because at 150k the api hot loop saturates before the database. *Proof:* 100k reconciled on Citus, with DB CPU split across the workers.

- **Edge + single-process replicas (H1), kept for horizontal scale, not for speed** (2026-10-02, `c911c03`/`157f5ff`). At 150k: ingest per api replica is balanced (max/mean 1.06, was 1.9 across uvicorn workers) and the rung now passes v3. But total CPU rose from 2.65 to 3.28 cores (the edge costs 0.51), p95 rose from 216 to 278 ms, and hot-loop lag p99 did not fall (18–27 ms). The perf architect's predicted 1.5–2× ceiling gain is **not demonstrated**. *Rejected:* uvicorn workers with SO_REUSEPORT, which balances only within one host. *Revisit:* if edge CPU becomes the bottleneck, use L4 `mode tcp` for `/ingest`.

- **The ceiling on the edge topology is 150k devices, and the bottleneck is PostgreSQL** (2026-10-02). At 200k (`evidence/capacity/rung-200k.json`, code 157f5ff) every report reconciled but p95 was 1,393 ms. The database ran at 1.94 cores (peak 2.4 of 3) while processors sat at 0.16. Next hypothesis: H2 (HOT upserts).

- **H2 kept: the grid cell replaces the device GiST** (2026-10-02, `009d8ed`). At 200k: HOT updates went from 2.1% to 98.6%, PostgreSQL CPU from 1.94 to 1.05 cores, and p95 from 1,393 to 448 ms. The rung now **passes** (`evidence/capacity/rung-200k-h2.json`). The GiST index had `idx_scan = 0`. *Next:* 300k.

- **300k on 4 processors: delivery exact, freshness lost; the processor tier is the ceiling** (2026-10-02 03:21, code 3f278e3, `evidence/capacity/rung-300k.json`). 18,000,000/18,000,000 acked, committed and reconciled in all 4 sessions; generator p99 schedule lag 11 ms. But processors committed about 50k/s against 60k/s offered. Lag grew to 2.3M records and end-to-end p50/p95 was 32/49 s. Processors ran at only 0.18 cores each, with batches full (2,000) and p50 102 ms, and PostgreSQL at 1.55 of 3 cores. So the limit is **serial round trips per owner**, not CPU anywhere. *Next:* the same rung on 8 processors (`rung-300k-p8`).

- **Replay is decided by persisted offset, not by row equality** (2026-10-02, after [2026-10-02-0330-review-0f4bb6c](ideas/2026-10-02-0330-review-0f4bb6c.md)). A `consumer_progress(topic, partition, persisted)` row advances in the batch transaction. Records at or below it are re-emitted in full, and records above it go through the watermark. This closes the multi-sample replay loss and FA-5 (ambiguous COMMIT); a client resend is stale again. *Rejected:* equality with the newest stored row (loses every earlier sample in the batch); a transactional outbox of emitted frames (writes every frame twice for the same guarantee). *Cost:* a replay may re-emit a record that was stale the first time, so events are a superset, never a loss.

- **`plan_cache_mode` is scoped to the two queries that need it** (2026-10-02): `SET` on `zone_occupancy` and `SET LOCAL` in the bbox snapshot. It is no longer a pool-wide knob that the processor pays for.

- **300k at f7b3aae was I/O-bound on benchmark debris, not a capacity reading** (2026-10-02 03:4x, `rung-300k-p8-progress`). `device_latest` held 2.0M rows from earlier runs, each with its own prefix: 395 MB against 256 MB of shared_buffers. The watermark SELECT averaged 47.6 ms, of which 140 ms of I/O was measured cold on 2,000 ids versus 13.5 ms warm. The upsert averaged 58.8 ms. p50 was 56 s. *Fix:* the benchmark deletes its own devices and vacuums; shared_buffers 512 MB. *Lesson:* compare rungs only on a table holding the same rows.

- **Metrics are Prometheus, one registry per role; lag comes from the broker** (2026-10-02, `5b4840f`, from [2026-10-02-0325-sre-lens](ideas/2026-10-02-0325-sre-lens.md)). *Rejected:* NATS scatter-gather (a stalled process silently left the totals); a module-global registry (every process exported every role's gauges, so `ProcessorStalled` fired on gateways); processor-reported lag (blind to unowned partitions). The observability stack is core, not a profile, because the benchmark's verdict depends on it.

- **Liveness is the only health signal** (2026-10-02, `8cb4c9c`). At 300k the api readiness check, which probed Kafka metadata with a 1 s timeout, failed on every saturated replica. HAProxy logged "backend 'api' has no server available", and 96 lanes reconnected and resent 0.48M reports. *Rejected:* dependency-probing readiness. When Kafka is down every replica is equally unable, so draining them only replaces per-request 503s with connection refusals; the alerts carry the dependency state. *Also:* edge checks moved to 5 s timeout, 2 s interval, 3 misses.

- **H5: freshness from `RETURNING old.reported_at`; PostgreSQL 17 → 18** (2026-10-02, `8cb4c9c`). It removes the watermark SELECT (47.6 ms per 2,000-record batch, the second-largest statement). *Rejected:* a `previous_reported_at` column, which would store a value only the returning statement needs. *Measurement:* `rung-300k-h5` (6 api, 8 processors). It also changes api 4→6, so the comparison is per-statement from pg_stat_statements, not end to end.

- **Benchmark harness: every wait is bounded** (2026-10-02). `rung-300k-p8-v4` hung for 20 min after its schedule ended: zones and devices were never cleaned and observers never stopped. The exact frame was not recovered (py-spy needs root on macOS), so I closed every unbounded wait: a shard deadline of the schedule plus 120 s, observer handshakes timing out at 15 s, and `stop` set in `finally`.

- **Citus re-shaped and re-sequenced** (2026-10-02, from the scale architect). Distributing `device_latest` on `device_id` was wrong. `MATCH_SQL` joins the batch's points with `geozones` only, so matching would stay on the coordinator, and each batch would touch every shard in a 2PC. The right shape keys `device_latest` and `consumer_progress` on the Kafka partition, with one shard per partition, so a partition's transaction is single-shard and matches locally against the reference `geozones`. On one machine it adds no cores, so it comes after the per-report CPU work (S1–S4) and is claimed as a shape proof, not throughput.

- **300k on 6 api and 8 processors (H5): the laptop is out of cores** (2026-10-02 04:19, `rung-300k-h5`). Every check failed except delivery reconciliation: 17.67M of 18M acked, 2.4M resent after 132 reconnects. api loop lag p99 hit 1.0 s and generator schedule lag p99 0.95 s. Median CPU summed to about 9.7 cores for the server, plus about 5 for 12 generator processes and 4 observers, against 14. After the schedule, PostgreSQL committed 148k/s, so the database is not the wall when it gets CPU. The upsert with RETURNING old averaged 70.6 ms per batch, and the watermark SELECT is gone. *Conclusion:* per-report CPU is the only lever on one machine → S1 (framing), then S2 (librdkafka).

- **One definition of a valid report: msgspec** (2026-10-02, `85b0ff9`). HTTP, frames and OpenAPI use the same `Report` Struct. *Rejected:* keeping pydantic for HTTP beside msgspec for sockets (two validators drift). The device-id pattern uses `\Z`, because Python's `$` accepts a trailing newline.

- **300k passes** (2026-10-02 04:28, code 85b0ff9, `rung-300k-s1`): 18M/18M, p95 753 ms, 0 resent. Server 6.41 cores (api 4 × 0.61, db 1.19, processors 8 × 0.14). Upsert mean 7.8 ms per batch of about 430 rows. This is the first rung under policy v4.

- **500k: delivery exact, processors the limit** (2026-10-02 04:50, ceae966, `rung-500k`). 30M/30M reconciled. Processors committed 58k/s against 100k/s offered and p50 was 88 s. api fell to about 26 µs per report with librdkafka (from about 40 with aiokafka). Batch p95 was 0.55 s while SQL was 64 ms of it, and the database idled at 1.7 of 3 cores. *Cause:* one serial chain per processor on a CPU-saturated host. *Fix:* S4 partition lanes (`cf5fd30`).

- **S4 kept: one lane per owned partition, started and cancelled only by the rebalance listener** (`cf5fd30`). *Rejected:* `gather` over the partitions of one poll, which is a barrier where the slowest partition holds the rest back; per-partition queues fed by a single poll, which need pause, resume and seek coordination. Concurrent `getmany(partition)` calls on one consumer are proven by the suite, including a joining processor that takes partitions without loss.

- **G5 failure campaign at 100k: no acknowledged report lost in any of the eight scenarios** (2026-10-02 05:45–06:45). Seven passed fault-v1. The NATS restart failed: open dashboards silently missed live events, because core NATS drops whatever is published while a gateway resubscribes. *Fix:* the gateway sends `resync` after reconnecting and the page reloads its snapshot (`fault-v2`); S1 then passed. *Rejected:* JetStream for live fanout. It would replay a gap no dashboard wants, since positions are superseded every 5 s, and would add a persistence tier to the hot path. *Rejected:* closing every dashboard on a NATS blip, which is the same information delivered with a reconnect storm.

- **The ceiling on this laptop is the host, between 300k and 500k** (2026-10-02). `rung-500k-s4`: PostgreSQL at 2.82 of 3 cores, server containers at 10.8 cores, host 99% busy. Idle-database probe: the upsert costs 16 ms per 2,000 rows; MERGE costs 17.5 ms, rejected. Further rungs need a second machine for the load.

- **Kafka's log lives on its volume; retention is 24 h or 1 GiB per partition; progress is keyed by topic ID** (2026-10-02, `ae23741`). Found while sizing DA2. Kafka wrote to `/tmp/kafka-logs` inside the container while `kafkadata` sat mounted and unused, so a recreation, unlike a restart, would drop every unprocessed report. Recreating the topic also exposed a latent defect: `consumer_progress` was keyed by topic name, so a same-name topic's offsets restarting at 0 would sit below the stored progress, and every new record would be taken for a replay and never persisted. *Proof:* 500 reports acked with processors stopped survived `--force-recreate kafka`, and 500 of 500 reached PostgreSQL. *Rejected:* 7-day retention, since at 300k devices the 45 GB disk holds about 2 h, so the byte cap governs. The alert threshold is 30 min of lag.

- **Graceful partition handover** (2026-10-02, `dc7073f`). S9 (half the processors stopped under load, then restarted) passed, but re-emitted 1,089 events. A revoked lane now finishes its in-flight batch and commits the offset, and is cancelled only past the publish deadline. Rerun: 48 re-emitted, p95 185 ms.

- **Kubernetes: liveness only, PDB 1, CPU HPA on api, KEDA-on-lag for processors** (2026-10-02, `58d314f`). The stateful tiers come from operators (Strimzi, CloudNativePG, NATS chart). The manifests are kubeconform-strict in the gate.

- **Security lens closed** (2026-10-02, `8b05a54`, `c862bbe`, from [2026-10-02-0835-security-lens](ideas/2026-10-02-0835-security-lens.md)).
  - *Critical:* matches per report were unbounded (1,000 world-sized zones → 2M rows per batch, a permanent poison partition). They are bounded at zone CRUD: radius ≤ 500 km and at most 50 overlapping zones per user. *Rejected:* a per-batch match limit, which is the original DoS bug in a new place.
  - *Gateway memory:* one byte budget with largest-backlog eviction. *Rejected:* shrinking every queue to 1 MiB, which would evict fast clients that merely burst.
  - *Edge limits:* keyed per user, since Docker NAT collapses client IPs.
- **One rule for future timestamps** (2026-10-02, `e97b1e0`). More than 30 s ahead of the server is a 422, and every accepted timestamp is stored as sent. This replaces X4's clamp to receive time. The clamp rewrote real reports under ordinary host/VM clock skew, so every dashboard checksum and the PostgreSQL latest check failed in the 300k tx1 runs ([loop-ledger](loop-ledger.md), round 18). It also added no protection, because ingestion is unauthenticated and a spoofer can send any position. *Rejected:* clamping to now + tolerance, which still rewrites data silently.
- **A lane owns its liveness** (2026-10-02, `e97b1e0`). Task, leave signal and last poll live on one `Lane` object, and the watchdog reads only lanes that still exist. Three separately mutated dicts let a revoked lane re-stamp its poll after the handover, and 40 s later the watchdog killed a healthy processor.
- **One database writer per processor; S4 lanes reversed** (2026-10-02, `bcce466`). The writer takes everything prefetched across the owned partitions, up to 10,000 records, in one transaction. A delivery stage publishes and commits offsets in batch order while the next batch is written. *Why:* lanes coupled concurrency to batch size. At 300k the upsert carried 247 rows per call at 34 µs per row, against 5.8 µs idle, so statement time per second doubled against `rung-300k-s1`. At 500k the lanes saturated PostgreSQL at 143 ms per upsert. The 500k serial-chain limit that motivated S4 is removed by the pipeline, not by concurrency. *Rejected:* fewer or bigger lanes, which keep the coupling. *Result* (`c0812d8`, `rung-300k-one-writer`): passed. p50/p95/p99 314/876/1,286 ms; statement time 1.59 s/s (was 2.9); PostgreSQL 1.25 cores (was 1.51); 432 rows per upsert, 8 ms per call. The per-row cost is still 18.6 µs against 5.8 µs idle, because the writer cycles as soon as data arrives, so batches stay near 430 at 300k.
- **300k with exact timestamps** (2026-10-02 07:58, `e97b1e0`, `rung-300k-exact-timestamps`, lanes tx=4). Every correctness check passed: 18M/18M committed, all 4 sessions reconciled with exact checksums, PostgreSQL holds every latest report, 0 resets, memory stable. Failed on latency only: p50/p95/p99 421/1,082/1,598 ms, DB statement time 2.9 s/s.
- **The writer always polls; one byte rule for frames; a fetch window for batches** (2026-10-02, `1cf61ae`, from [2026-10-02-0845-review-bcce466](ideas/2026-10-02-0845-review-bcce466.md)). *Why:* a pause gate outside `getmany` lets aiokafka stop rejoining a member idle past `max_poll_interval`. Unbounded position frames can exceed NATS `max_payload`, and a batch spans every owned partition. A revoke past the deadline let old batches commit into the next generation; now both stages are cancelled and restarted. With `fetch_min_bytes=1`, batches had no floor. *Rejected:* AIMD batch shrinking after a DB error.
- **Processor faults on one writer pass fault-v2** (2026-10-02, `bcce466`): s3 kill (p95 186 ms), s4 pause (p95 120 ms, 59 replayed), s9 half stopped then started (p95 123 ms). Files: `evidence/faults/*-one-writer.json`.
- **Fetch window disproved; batching stays self-clocked** (2026-10-02, `c459ea4`, `rung-300k-batch-window`). A 100 ms `fetch_max_wait_ms` with a large `fetch_min_bytes` doubled batches (432 → 999 rows) without lowering the cost per row (about 18 µs either way; statement time 1.62 against 1.59 s/s). Kafka CPU rose from 0.64 to 1.27 cores, and p95 from 876 to 1,071 ms. Under load the cost per row is CPU on a saturated host, not per-statement overhead.
- **s9 on the restart-on-timeout handover** (`1cf61ae`): passes fault-v2, p95 139 ms, 0 resent.
- **Citus shape under one writer** (2026-10-02, design page v8). The shard key stays the Kafka partition. Partition lanes made each transaction single-shard; a writer spanning partitions would make it cross-shard. So under Citus the writer splits its batch into one transaction per worker it touches (progress, upsert and match together), and every commit stays single-node whatever the assignor hands out. *Rejected:* returning to per-partition transactions, which reintroduces the per-row cost measured in `rung-300k-exact-timestamps`.
- **Alerts are proven by a drill, not by promtool alone** (2026-10-02, `01ad9d9`, `evidence/alerts-drill.json`). The first drill found two rules that could never fire. `PartitionsUnowned` was a `sum()` over series that vanish when every processor is gone (fix: `or vector(0)`). `TargetDown` used `up == 0` on DNS-discovered replicas, which leave discovery instead of reading 0. *Decision:* a lost replica is not an alert. `RoleDown` fires when no replica of a role answers, and `TargetDown` covers only static targets. *Rejected:* per-role expected replica counts in Prometheus, a second copy of the compose/k8s replica settings that would drift. Fired after: BatchesFailing 8.5 s, RoleDown:processor 43 s, PartitionsUnowned 67 s, RoleDown:api 43 s, TargetDown:edge 38 s.
