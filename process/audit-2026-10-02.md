# Fleetline submission review: verdict and rework list

Verdict: the backend core (ingestion pipeline, PostGIS matching, multi-session WebSocket registry, Docker) is strong, above Middle+. As a test-task submission, though, the repo is noisy and openly shows it was generated by an agent. It also has one real design bug, proven live: any mock user can stop ingestion for the whole fleet just by creating overlapping zones. Before the repo goes to anyone: fix the fanout budget, delete the scope creep and agent artefacts, and split main.py into routers with full type hints. Do not touch the pipeline, the session registry or the Docker setup.

Repo: this repository, branch geo-tracking-test-task @ b340c42 (https://github.com/NonSmiIe/geo-tracking-test-task). Assignment: the assignment (TestTask.docx). Prior work: [plan-2026-10-01](plan-2026-10-01.md), [report-2026-10-02](report-2026-10-02.md), [note-2026-10-02](note-2026-10-02.md).

## Proven defect: zone overlap stops ingestion for everyone

`pipeline.py` raises `OutputOverload` when one batch produces more than `max_matches` (4,000) matches or 1 MiB of output. The whole batch is rolled back and every request in it gets 503. At 200 reports per batch, a user with 21 or more zones covering the fleet pushes every batch past the limit.

Live probe against the running stack (127.0.0.1:8097): user `probe-dos` creates 60 zones of 10 km around Riga, then sends 400 concurrent single reports, a quarter of them at latitude 10 (outside every zone). Result: **400/400 → 503 fanout_budget_exceeded**, including devices outside every zone. After the zones are deleted, the same traffic gives 400/400 → 200. Counter `output_rejected: 400`. The probe zones were deleted afterwards.

`tests/test_backpressure.py::test_output_overload_rolls_back_and_emits_no_alerts` locks this in as intended behaviour. The benchmark used a single coverage zone, so the 10k-zone spatial spike never tested dense overlap.

Correct design: device state ingestion and alert delivery are independent. Matches are real output, so they must never roll back a position commit. Put the bound where the load comes from: a per-user zone quota at CRUD, and per-connection queue limits, which already exist and evict slow sockets. Split large alert bursts into frames, which `frames()` already does. Delete `max_matches` and `output_bytes` from the processing transaction, and delete the test that locks in the rollback.

## Rework

- **Scope creep, delete it.** The OpenAI assistant (`assistant.py`, `/assistant`, the `openai` dependency, its tests), `/insights`, `PRODUCT.md`, `DESIGN.md`, `.impeccable/`, `.agents/skills/drive-fleet` (it names `mcp__playwright__browser_run_code_unsafe`) and `scripts/ui_verify.js`. None of it was asked for; frontend is explicitly not evaluated. It adds attack surface and review noise, and it reveals the agent.
- **Agent artefacts in the README.** "The publishing account currently has repository access…", "Impeccable's direction roll assigned candidate five", the template CI in `ci/` instead of `.github/workflows/`. Activate CI properly or remove it.
- **evidence/: 4 MB of raw JSON and PNG**, three baseline runs of about 7k lines each, failed runs included. Keep one short `BENCHMARK.md` with the final numbers and the command; the raw dumps do not belong in the submission.
- **Structure.** `main.py` is a 281-line `create_app` closure holding every route. The criteria name "separation of concerns": split it into `api/locations.py`, `api/geozones.py`, `api/ws.py`, `api/health.py` with dependencies.
- **Type hints.** 60 of 65 functions in `geo_tracking/` have no return annotation; `spatial.match_reports(session, reports, limit)` is fully untyped; geography columns are `Mapped[object]`. The criteria name type hinting explicitly.
- **Hand-rolled `Admission` ASGI middleware** (body buffering, deadline, byte budget, applied to static and GET too). Replace it with uvicorn `--limit-concurrency` plus a body limit only on `/locations*`. Less code, same guarantees.
- **Three migrations for a fresh repo** (001 creates an index that 003 drops). Squash them into one initial migration.
- **Radius buckets** (CROSS JOIN over power-of-two buckets plus btree_gist) are correct and measured, but non-standard. The standard approach is a GiST index on the zone footprint (`ST_Buffer(center, radius_m)` as a stored geography), with an `ST_Intersects` candidate filter followed by exact `ST_DWithin`. That is one index and one predicate, with no bucket arithmetic for a reviewer to decode.

## Keep

- One microbatch processor: watermarks, first-wins duplicates, matching every fresh sample before collapsing to latest-only, a single `unnest` upsert. Shared `AsyncSession` is avoided; the pool is 5 with no overflow; the transaction is closed before fanout.
- Spatial: `geography(Point,4326)`, lon/lat order, set-based `ST_DWithin` in SQL with no Python distances. Tests run on real PostGIS: boundary, high latitude, antimeridian, swapped coordinates.
- WebSockets: `user → connection_id → Connection`, a bounded queue and exactly one writer per connection, frames pre-serialised once, non-blocking fanout, only the slow socket evicted, siblings survive.
- Generator: open loop on a monotonic schedule that never slows down to match the server, realistic drift, bounded connector and queue, honest counters.
- Docker: non-root, read-only rootfs, cap_drop ALL, DB not published, healthchecks, pinned images, tests in an isolated `geo_test`.
- Single process with no Redis: justified by measurement (1.8M/1.8M at 2,000/s, p95 92 ms, 120 MiB). The README says honestly that adding workers needs a different architecture. Adding a broker just to tick a box would make it worse.

## About the experiment

The agent followed the engineering discipline (adversarial plan, measurements, honest failed runs) at a high level. It did not keep scope: it spent effort on UI, design rituals, AI features and evidence theatre, while a bound sitting in the wrong layer survived three reviews. The 10k-zone spike measured the query but not the semantics of overlap.
