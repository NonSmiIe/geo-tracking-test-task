Build a two-container submission: one FastAPI/Uvicorn process and PostgreSQL with PostGIS. Use bounded admission, one asynchronous microbatch processor, metre-correct spatial queries, and independent bounded writers for every WebSocket session. The architecture is a candidate to prove with adversarial tests and measured load; it is not a claim that one process already sustains the required throughput.

Requirements and technical evidence: [requirements and source verification](research-2026-10-01.md). Source assignment: the assignment (TestTask.docx). This plan incorporates the explicitly requested adversarial architecture subagent and a separate parent review. Implementation is now in the standalone geo-tracking-test-task repository. See the audit and eventual closing report for measured state.

## Contract and scope

- Use a shared demo fleet: all identified users see fleet locations; only zone owners see their zones and alerts. Device ownership is unspecified in the assignment, so make this assumption explicit in the README.
- Emit an inside_report alert for each accepted fresh position and each matching active zone, including repeated reports inside the same zone. Do not implement entry-only deduplication.
- Mock identity uses X-User-ID on REST. For the browser WebSocket use a mock user ID query parameter, because native browser WebSockets cannot set arbitrary headers. Resolve identity at connection setup; message payloads cannot choose alert recipients.
- A sample is identified by (device_id, UTC timestamp). Equal-timestamp duplicates use deterministic first-payload-wins semantics. Stale reports at or before the persisted device watermark do not change the live map or emit alerts. Return their status explicitly. This freshness policy is an implementation decision, not an assignment requirement.
- Latest device state and zones survive restart. WebSocket events are live and ephemeral; offline replay, a full movement-history store and exactly-once delivery are outside the assignment.
- Run exactly one Uvicorn worker. Multiple workers would invalidate local routing and processor ownership; cross-process delivery is a separate architecture change, not an extra worker flag.

## Data and public interfaces

geozones: UUID id, user_id, name, centre geography(Point,4326), positive radius_m, active, version incremented on edit. Index user_id for ownership operations and centre with a partial GiST index for active zones. Enforce finite coordinates and radius and latitude/longitude ranges at the input boundary and essential invariants in the database.

device_latest: device_id primary key, position geography(Point,4326), reported_at timestamptz. Construct PostGIS points in longitude, latitude order. A device position index is unnecessary for this initial latest-state snapshot interface; the added private occupancy insight uses its own GiST position index.

- POST /locations accepts one report; POST /locations/batch accepts a capped array. Benchmark both separately; the primary load scenario exercises the single-report endpoint so client batching cannot conceal request overhead.
- POST and GET /geozones; GET, PATCH and DELETE /geozones/{id}. Every query includes user_id; another owner's ID behaves as absent.
- GET /devices/latest returns the current shared fleet snapshot.
- WS /ws?user_id=... streams locations frames and inside_report alert frames. Reports and alerts carry device ID and timestamp; alerts also carry zone ID and version. Batched frames preserve all accepted report samples.
- GET /health/live and /health/ready distinguish process liveness and database availability. Include a small metrics endpoint for pipeline and load evidence.

The browser opens its WebSocket first, then loads latest state. Merge snapshot and stream positions by timestamp so a slower snapshot cannot overwrite fresher data. Process alerts independently from map timestamp deduplication. This reconstructs current state on reconnect; it does not replay missed alerts.

## Ingestion and commit sequence

HTTP request → validation and bounded admission → bounded ingress queue → one processor → database transaction → commit → enqueue frames to every healthy recipient session → resolve request.

Start with 100–250 reports per microbatch and a 25–50 ms flush deadline. These are initial tuning values. Queue size, HTTP concurrency, request body size and admitted sockets all need explicit bounds. A full queue returns 503 with Retry-After instead of building an unbounded list of waiting requests. Keep HTTP admission separate from the allowed dashboard WebSocket count.

Within one transaction, read the previous device watermarks, deterministically remove equal-key duplicates, and retain every distinct report newer than its prior watermark. Evaluate every retained report for geozone alerts. Only then choose the maximum timestamp per device for the latest-state upsert. Several fresh samples for one device in a batch must each produce their own matching alerts.

Single processor ownership prevents concurrent batches from racing watermark reads and writes. It does not justify sharing one mutable AsyncSession with unrelated tasks. Give CRUD requests their own short sessions; give each processing transaction its own session. No session or database connection lives for the duration of a WebSocket.

An HTTP 200 means processing completed, accepted latest state committed, and events were placed in the recipient snapshot's queues, except connections explicitly closed for overload. It does not mean browsers acknowledged delivery. Return accepted, duplicate or stale status. A crash after database commit but before enqueue can lose live events; a timeout or disconnect after admission can leave the caller uncertain whether processing committed. Document these boundaries; do not claim atomic database-plus-WebSocket delivery.

On database errors roll back and fail the affected requests; send no uncommitted events. On shutdown stop admission, drain within a fixed deadline, and close sockets. If the processor dies unexpectedly, mark the application unready and fail pending work rather than leaving request futures hanging.

## Spatial strategy and proof

Use geography(Point,4326) and exact ST_DWithin(zone.centre, sample.position, zone.radius_m), keeping distance units in metres. Perform a set-based batch query, not one database round trip for every sample-zone pair and not Python distance calculations.

Different radii per zone require a selective candidate strategy. The maximum-radius spike failed under a global outlier: 200 reports against 10,000 zones took 2,090 ms, versus 1.638 ms without the outlier. Replace it with generated power-of-two radius buckets and a partial multicolumn GiST index on (radius_bucket, centre), using btree_gist for the bucket. Each bucket has its own conservative search distance, followed by the exact zone-radius ST_DWithin predicate. Bucket 25 covers global WGS84 distance and permits larger zone radii without an arbitrary semantic cap. The implemented query measured 13.6 ms without the outlier and 25.123 ms with it on the same fixture; retain the full execution plans and verify equality against the exact predicate.

Run EXPLAIN (ANALYZE, BUFFERS) on the actual parameterized query and preserve candidate counts and runtime. Dense true overlap still has genuine output cost and must hit explicit precommit budgets instead of silent truncation.
Use one SQLAlchemy async engine with a bounded pool; start pool_size=5, max_overflow=0 and a finite checkout timeout, then tune using observed wait time. Limit concurrent CRUD database work and reserve enough pool capacity for the processor. Release transactions before network sends.

Bound the matching result itself. Overlapping zones can produce batch_size × zone_count rows even with a bounded ingress queue. Set a documented per-processing-batch match count and serialized output byte budget; retrieve at most match_budget + 1 rows. A count or byte overflow rolls back the entire batch and returns 503 with fanout_budget_exceeded. Serialize and check output before commit. Do not accept reports and silently truncate their alert matches. Pick and publish concrete budgets during the spatial spike using named memory limits; dense-output overload is an explicit tested envelope. Splitting oversized batches can improve utilization later but cannot eliminate the final bound for a single pathological report.

Primary references: [PostGIS ST_DWithin](https://postgis.net/docs/ST_DWithin.html), [SQLAlchemy async sessions](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html), [SQLAlchemy pooling](https://docs.sqlalchemy.org/en/20/core/pooling.html).

## WebSocket state and backpressure

Registry shape: user_id → connection_id → Connection. Every connection owns its bounded FIFO queue, one writer coroutine, one receive/disconnect task and cleanup. Removing a connection must not remove that user's other sessions.

Fanout snapshots eligible connections and enqueues immutable pre-serialized frames without awaiting network sends. Serialize the common fleet frame once; build private alert frames by user. Yield during large local fanout work so enqueue loops cannot monopolize the event loop.

Each writer sends in order with a deadline. Queue limits cover both frame count and bytes, and large alert batches are split into capped frames. An empty connection queue must fit one complete maximum permitted batch burst, including its locations and private alerts. Check capacity for that full burst before enqueue; yielding is not a substitute for capacity. On backlog overflow or send timeout, close and remove only the affected connection, recording the reason. A close handshake also has a deadline. Never silently drop alert frames, overwrite unsent events with newer map positions or spawn one task per send without bounds.

Test two sessions for user A and one for B, then a deliberately non-reading session. Both healthy A sessions receive the same private alerts; B receives none of A's alerts; the slow connection cannot stall healthy streams or ingestion. The local-registry deployment limitation is documented in [FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/).

## Acceptance and benchmark matrix

Use real PostGIS integration tests, not SQLite or mocked distances. Check inside/outside/on-boundary metres, longitude/latitude reversal, high latitudes, antimeridian, disabled/deleted zones, overlapping zones and ownership filtering. Check duplicate keys, stale samples, two fresh same-device samples in one batch and a transient inside position followed by outside. Boundary fixtures should be generated using PostGIS distance functions and tolerances appropriate to floating-point coordinates.

Delivery tests reconcile accepted report IDs and expected alert tuples with received frames for healthy subscribed sessions. Check that one session disconnect leaves its sibling intact, a slow reader is evicted, and no frame is sent before a failed transaction commits. CRUD visibility is defined by the processor's transaction snapshot; an already evaluated alert can arrive after a later zone deletion, which must be documented and tested.

| Scenario | Device report rate | Zones and sessions | Purpose |
| --- | --- | --- | --- |
| Small deterministic run | 100–1,000 devices | Two users, three sessions, scripted zone crossings | Exact correctness and event reconciliation |
| Baseline sustained | 10,000 / 5 seconds = 2,000 per second | Explicitly publish zone count, radius distribution, overlap and session count | Required scale with full delivery checks |
| Faster sustained | 10,000 / 2 seconds = 5,000 per second | Same named fixture | Headroom and measured capacity boundary |
| Fanout sweep | Baseline rate | 1, 10 and 100 healthy sessions, two sessions per user where possible | Outbound scaling and serialization cost |
| Spatial sweep | Baseline rate | 100, 1,000 and 10,000 active zones; sparse and dense overlap; one giant-radius outlier | Candidate cost versus true output explosion |
| Burst and overload | Synchronized reports, then exceed sustainable offered rate | Normal and non-reading clients | Bounded memory, explicit rejections and healthy recovery |
| Faults | Baseline then disconnect/restart | DB outage, app restart, session churn | Readiness, no phantom events and reconstructable latest state |

Initial acceptance target, to be confirmed against named hardware: a 15-minute baseline run with no unexplained missing events for healthy sessions, no unintended overload rejections, stable bounded memory, bounded queue depth and database connections, and p95 report-to-WebSocket receive latency below one second. This latency is a proposed engineering target, not a promise from the assignment. Publish actual results and failed envelopes rather than claiming unlimited scalability.

Record HTTP and end-to-end latency distributions, offered and accepted rates, generator deadline misses, queue high-water marks, database pool waits and query time, CPU/RSS, loop lag, outbound bytes, alert count and slow-client disconnections. Retry traffic is accounted separately from original reports. Retention, offline replay, multi-process routing and cross-process delivery remain explicit limits of this submission.

## Adversarial rejection criteria

Reject one database operation per zone per report, a connection per device, a shared AsyncSession across concurrent tasks, sequential awaited socket broadcasts, unbounded queues/tasks, pre-evaluation latest-only reduction, edge-only alerts, and multi-worker deployment with a local registry. Redis Pub/Sub alone would not add durable replay. If measurements show the single-process envelope is insufficient, redesign from the measured bottleneck; do not add a broker by default or merely increase the pool.
